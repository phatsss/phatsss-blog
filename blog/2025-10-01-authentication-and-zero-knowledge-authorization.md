<!-- truncate -->

## 1. Advanced Authentication Architecture: The PASETO Hybrid Model

The deployment of a production-grade authentication and authorization system requires a rigorous, decoupled architecture that leverages the security strengths of both the server-side rendering (SSR) framework and the dedicated backend API. This report details the implementation of such a system, utilizing **Next.js** (App Router/TypeScript) coupled with **Next-Auth**, and a **Golang API** employing **PASETO** (Platform-Agnostic Security Tokens) for superior integrity and confidentiality.

### 1.1. Executive Summary and System Security Goals

The fundamental goal is to establish a highly resilient authentication framework that prioritizes security, minimizes client-side exposure, and maintains a smooth user experience across both SSR and client-side rendering (CSR) contexts. The architecture enforces three paramount security principles: **Secure Session Management**, strict **Refresh Token Rotation (RTT)**, and **Server-Controlled Authorization (Zero-Knowledge)**.

In this setup, the **Golang backend** functions as the ultimate security authority, responsible for secure token generation, validation, and managing the refresh token lifecycle. **Next-Auth**, conversely, acts as the session state mediator and RTT coordinator within the Next.js environment. Next-Auth provides essential security features by default, including CSRF protection, secure cookie management, and centralized session handling.

### 1.2. Architectural Context: Decoupled Full-Stack Token Flow

Next-Auth’s role is essential as a **Secure Mediator**, handling the complexity of session encryption and token management within the Next.js server environment. The interaction begins with the use of the **Credentials Provider**, which is crucial for delegating the primary authentication (username and password validation) to the external Golang API. Next-Auth then consumes the token pair generated by the Go service, treating the external API as the single source of authentication truth.

#### Token Separation Strategy

Security is maximized through strict token separation and controlled storage:

* **Access Token (PASETO V2.Local):** This token is **short-lived** (e.g., 5 to 15 minutes) and is used for authorizing requests to protected API endpoints. It is stored securely inside **Next-Auth’s encrypted session cookie**. This means the client-side JavaScript does not have direct access to the raw token string, except via the Next-Auth `useSession()` hook, which exposes the data from the server-managed, encrypted cookie.
* **Refresh Token (Opaque/PASETO ID):** This token is **long-lived** (e.g., 7 to 30 days) and is used exclusively for obtaining new Access Token pairs. Critically, it is managed exclusively by the Golang backend and stored in an **HTTP-only, Secure, SameSite=Strict cookie**. Since it is `HttpOnly`, the refresh token is never exposed to client-side JavaScript (`document.cookie`), which prevents theft via **Cross-Site Scripting (XSS)** attacks.

### 1.3. Comparison: PASETO (Paseto Version 2 Local) vs. JWT Security Rationale

The selection of **PASETO** over standard JSON Web Tokens (JWTs) is a deliberate security enhancement. Traditional JWTs primarily use digital signatures (JWS), making them tamper-proof but fundamentally **readable** by anyone who intercepts them over the network.

**PASETO V2 Local**, by contrast, is a cryptographically superior choice because it mandates **authenticated encryption** using modern ciphers like ChaCha20-Poly1305 and symmetric keys. This ensures that the token payload is not only tamper-proof but also **opaque**—meaning its contents cannot be read by intermediate observers or the client without possession of the secret key. This inherently reduces information leakage risk, which is a major concern when designing zero-knowledge authorization models.

The enforcement of this **Zero-Knowledge model** is enhanced by PASETO V2.Local. Even if the access token contained only minimal claims (such as a user ID or session ID), the encryption ensures that these minimal claims are also protected from inspection. This layer of defense goes beyond the security offered by a signed-but-unencrypted JWT, reinforcing confidentiality.

Furthermore, **Refresh Token Rotation (RTT)** is essential because PASETO documentation indicates that the tokens alone cannot prevent replay attacks. By enforcing a short lifespan on the encrypted PASETO Access Token (e.g., 5–15 minutes) and implementing the **“use-once” principle** enforced by RTT on the refresh token, the window of opportunity for an attacker using a stolen token is drastically reduced. If a refresh token is compromised, its subsequent usage by the legitimate user triggers cascade revocation of the compromised token and all derivative sessions, enhancing session integrity.

## 2. Golang Backend Implementation: The Security Authority

The Golang API is designed using the **Single Responsibility Principle (SRP)** of SOLID, ensuring that token creation, validation, and authorization decisions are isolated and robustly managed.

### 2.1. PASETO Services and Key Management (SOLID: SRP)

A dedicated service, `PasetoMaker`, handles all cryptographic operations.

**Code Implementation: `paseto_maker.go`**

```go
package token

import (
	"fmt"
	"time"

	"[github.com/aead/chacha20poly1305](https://github.com/aead/chacha20poly1305)"
	"[github.com/o1egl/paseto](https://github.com/o1egl/paseto)"
	"[github.com/google/uuid](https://github.com/google/uuid)"
)

// PasetoMaker defines the interface for PASETO token management
type PasetoMaker interface {
	CreateToken(userID string, duration time.Duration) (string, *Payload, error)
	VerifyToken(token string) (*Payload, error)
}

// Payload structure used inside the PASETO (minimal claims)
type Payload struct {
	ID        uuid.UUID `json:"id"`
	UserID    string    `json:"user_id"`
	CreatedAt time.Time `json:"created_at"`
	ExpiryAt  time.Time `json:"expiry_at"`
}

// NewPayload creates a new token payload
func NewPayload(userID string, duration time.Duration) (*Payload, error) {
	tokenID, err := uuid.NewRandom()
	if err != nil {
		return nil, err
	}
	payload := &Payload{
		ID:        tokenID,
		UserID:    userID,
		CreatedAt: time.Now(),
		ExpiryAt:  time.Now().Add(duration),
	}
	return payload, nil
}

// PasetoMaker implementation
type PasetoMakerImpl struct {
	paseto *paseto.V2
	symmetricKey []byte
}

// NewPasetoMaker validates the symmetric key length and initializes the maker
func NewPasetoMaker(symmetricKey string) (*PasetoMakerImpl, error) {
	// Crucial check: symmetric key must be 32 bytes for ChaCha20-Poly1305 [5]
	if len(symmetricKey) != chacha20poly1305.KeySize {
		return nil, fmt.Errorf("symmetric key size must be %d characters", chacha20poly1305.KeySize)
	}
	maker := &PasetoMakerImpl{
		paseto:       paseto.NewV2(),
		symmetricKey: []byte(symmetricKey),
	}
	return maker, nil
}

// CreateToken generates an encrypted PASETO V2.Local token [5]
func (maker *PasetoMakerImpl) CreateToken(userID string, duration time.Duration) (string, *Payload, error) {
	payload, err := NewPayload(userID, duration)
	if err != nil {
		return "", payload, err
	}
	// Note: Encrypting the payload with the symmetric key (V2.Local)
	token, err := maker.paseto.Encrypt(maker.symmetricKey, payload, nil) 
	return token, payload, err
}

// VerifyToken decrypts and validates the PASETO token [5]
func (maker *PasetoMakerImpl) VerifyToken(token string) (*Payload, error) {
	payload := &Payload{}
	// Decrypt the token payload using the symmetric key
	err := maker.paseto.Decrypt(token, maker.symmetricKey, payload, nil)
	if err != nil {
		return nil, fmt.Errorf("invalid token: %w", err)
	}
	// Check standard validity (expiry) defined in Payload struct
	if time.Now().After(payload.ExpiryAt) {
		return nil, fmt.Errorf("token expired")
	}
	return payload, nil
}
````

### 2.2. Secure Refresh Token Rotation (RTT) Implementation

The **RTT mechanism** is central to mitigating session hijacking and token theft. This implementation requires a persistent store (e.g., Redis or database) to manage refresh token lineage and state.

**Strategy:** The **"Use-Once" principle** is strictly enforced. When the client sends an expired access token and the active refresh token (`RT1`) to the `/refresh` endpoint, the service must perform the following atomic steps:

1.  Validate `RT1` and look up the session state.
2.  Generate a new PASETO Access Token (`AT2`) and a new Refresh Token (`RT2`).
3.  Immediately **revoke or mark `RT1` as used/expired** in the persistent store.
4.  Issue `AT2` and link `RT2` to the session, establishing `RT2` as the new valid token.

If an attacker attempts to reuse `RT1`, the revocation logic triggers **cascade revocation**, invalidating all subsequent tokens (`RT2`, `RT3`, etc.) associated with that session lineage, effectively locking out the compromised session and signaling a potential breach.

**Code Implementation: RTT Core Logic (`token_service.go` concept)**

```go
// ValidateAndRotateToken handles the RTT process
func (ts *TokenService) ValidateAndRotateToken(oldRefreshTokenID string, userID string) (
    newAccessToken string, newRefreshTokenID string, accessTokenExpiry time.Time, err error) {
    
    // 1. Check if the old refresh token ID is valid and not used (Use-Once Principle)
    session, err := ts.Repository.GetSession(oldRefreshTokenID)
    if err != nil || session.IsRevoked() {
        // Critical: If invalid or revoked, perform cascade revocation and fail.
        ts.Repository.RevokeAllSessionTokens(userID)
        return "", "", time.Time{}, fmt.Errorf("invalid or compromised refresh token")
    }

    // 2. Revoke the old token (RT1)
    ts.Repository.MarkTokenUsed(oldRefreshTokenID) // RT1 is now invalidated
    
    // 3. Generate new PASETO Access Token (AT2)
    atDuration := 15 * time.Minute
    newAccessToken, _, err = ts.PasetoMaker.CreateToken(userID, atDuration)
    
    // 4. Generate new Refresh Token (RT2) ID and store in DB/Redis
    rtDuration := 30 * 24 * time.Hour
    newRefreshTokenID = uuid.NewString() // Generate new opaque ID for refresh token
    ts.Repository.CreateNewSession(newRefreshTokenID, userID, rtDuration)
    
    return newAccessToken, newRefreshTokenID, time.Now().Add(atDuration), nil
}
```

### 2.3. Authentication Endpoints and Cookie Handling

**Endpoint Code: `/login` (POST)**

```go
func LoginHandler(w http.ResponseWriter, r *http.Request) {
    //... validation logic (User credentials check)...
    userID := "user-123" // Assume successful authentication

    // 1. Create PASETO Access Token
    accessToken, _, _ := pasetoMaker.CreateToken(userID, 15*time.Minute)
    
    // 2. Create Refresh Token ID and store session data
    refreshTokenID := uuid.NewString()
    tokenService.Repository.CreateNewSession(refreshTokenID, userID, 30*24*time.Hour)

    // 3. Set Refresh Token in HttpOnly cookie [4, 8]
    http.SetCookie(w, &http.Cookie{
        Name:     "refresh_token",
        Value:    refreshTokenID, // Store only the opaque ID, not the PASETO token itself
        Expires:  time.Now().Add(30 * 24 * time.Hour),
        HttpOnly: true,  // CRITICAL: Prevents client-side JS access (XSS mitigation)
        Secure:   true,  // CRITICAL: Requires HTTPS
        SameSite: http.SameSiteStrict, // Best practice for CSRF defense
        Path:     "/",
    })

    // 4. Return Access Token and expiry to Next-Auth [1]
    response := map[string]interface{}{
        "accessToken": accessToken,
        "expiresIn":   900, // 15 minutes in seconds
        "user":        map[string]string{"id": userID, "username": "TestUser"},
    }
    json.NewEncoder(w).Encode(response)
}
```

**Endpoint Code: `/refresh` (POST)**

```go
func RefreshTokenHandler(w http.ResponseWriter, r *http.Request) {
    // 1. Middleware/Handler extracts HttpOnly Refresh Cookie [7]
    cookie, err := r.Cookie("refresh_token")
    if err != nil {
        w.WriteHeader(http.StatusUnauthorized)
        return
    }
    oldRefreshTokenID := cookie.Value

    // (Internal lookup for user ID associated with the old token ID)
    userID := "user-123" 

    // 2. Perform RTT logic
    newAccessToken, newRefreshTokenID, newExpiry, err := tokenService.ValidateAndRotateToken(oldRefreshTokenID, userID)
    
    if err != nil {
        w.WriteHeader(http.StatusUnauthorized) // Unauthorized (401) if rotation fails (e.g., token reused)
        return
    }

    // 3. Set NEW Refresh Token in HttpOnly cookie [8]
    http.SetCookie(w, &http.Cookie{
        Name:     "refresh_token",
        Value:    newRefreshTokenID,
        Expires:  newExpiry, // Set appropriate long expiration
        HttpOnly: true,
        Secure:   true,
        SameSite: http.SameSiteStrict,
        Path:     "/",
    })

    // 4. Return NEW Access Token payload to Next-Auth
    response := map[string]interface{}{
        "accessToken": newAccessToken,
        "expiresIn":   int(newExpiry.Sub(time.Now()).Seconds()),
    }
    json.NewEncoder(w).Encode(response)
}
```

### 2.4. Authorization Middleware (The Gatekeeper)

The Go authorization middleware acts as the **Policy Enforcement Point (PEP)**. It strictly verifies the PASETO Access Token and then executes policy checks based on the request context.

```go
func AuthMiddleware(maker token.PasetoMaker) gin.HandlerFunc {
    return func(c *gin.Context) {
        // 1. Extract PASETO Access Token from Authorization header (Bearer scheme)
        authHeader := c.GetHeader("Authorization")
        //... basic header format check...
        accessToken := authHeader[7:] // Assume "Bearer " prefix

        // 2. Validate PASETO Token
        payload, err := maker.VerifyToken(accessToken)
        if err != nil {
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "Unauthorized"})
            return
        }

        // 3. Authorization Logic (Policy Check)
        // Extract minimal claims (UserID)
        userID := payload.UserID
        resource := c.FullPath() // e.g., /api/admin/reports
        action := c.Request.Method // e.g., GET, POST

        // Query the centralized Policy Engine (DB or Cache lookup)
        if !PolicyEngine.IsAuthorized(userID, resource, action) {
            c.AbortWithStatusJSON(http.StatusForbidden, gin.H{"error": "Forbidden access"})
            return
        }

        // If authorized, attach context for downstream handlers
        c.Set("userID", userID)
        c.Next()
    }
}
```

This design ensures that authorization decisions are always **server-controlled**, preventing the use of stale or compromised permission data, aligning perfectly with the **Zero-Knowledge mandate**.

### 3.2. The Critical `callbacks.jwt` Implementation

The `jwt` callback is the state machine responsible for managing the token lifecycle and coordinating RTT. It determines what is stored within the encrypted Next-Auth session cookie.

#### Initial Sign-in and Refresh Logic

The **RTT coordination logic** relies on checking the `accessTokenExpires` timestamp. If the token is nearing expiration, the `refreshAccessToken` function is invoked on the Next.js server. This is crucial because it ensures the server-side logic handles the refresh token, which is stored in an `HttpOnly` cookie. The underlying network layer automatically forwards the browser's `HttpOnly` refresh cookie to the Go API when the server-side fetch request is made to the `/refresh` endpoint.

```typescript
// lib/auth.ts (inside authOptions)
callbacks: {
    // 1. Logic for Access Token Refresh [11]
    async jwt({ token, user, account }) {
        // Initial sign-in (user/account are available)
        if (account && user) {
            return {
               ...token,
                accessToken: user.accessToken,
                accessTokenExpires: user.accessTokenExpires,
                // Only minimal user data transferred
                user: { id: user.id, username: user.name }, 
            };
        }

        // Return previous token if AT has not expired
        if (Date.now() < token.accessTokenExpires) {
            return token;
        }

        // 2. AT expired, attempt to refresh
        return refreshAccessToken(token); 
    },
    //... session callback definition below
},

// RTT Helper function running on the Next.js server
async function refreshAccessToken(token: JWT) {
    try {
        const response = await fetch(`${process.env.BACKEND_API_URL}/refresh`, {
            method: 'POST',
            // Crucially, headers are omitted, relying on automatic cookie forwarding
            // of the HttpOnly 'refresh_token' by the Next.js server context.
        });

        const refreshed = await response.json();

        if (!response.ok) {
            // RTT failed (e.g., refresh token revoked or expired by Go backend)
            throw new Error("RefreshAccessTokenError");
        }

        // Rotation succeeded: Go API returned a 200, set a new HttpOnly refresh cookie, 
        // and returned the new PASETO Access Token.
        return {
           ...token,
            accessToken: refreshed.accessToken,
            accessTokenExpires: Date.now() + refreshed.expiresIn * 1000,
            error: null, // Clear any previous error
        };

    } catch (error) {
        // Propagate error to trigger client-side sign-out flow [11]
        return {...token, error: "RefreshAccessTokenError" as const };
    }
}
```

### 3.3. Session Callback and Client-Side Error Handling

The `callbacks.session` function is responsible for structuring the final object accessible to the client via `useSession()`. It transfers only minimal, necessary data, specifically excluding the Refresh Token ID.

```typescript
// lib/auth.ts (inside authOptions)
async session({ session, token }) {
    if (token) {
        session.user = token.user;
        session.accessToken = token.accessToken; // Client uses this for CSR requests
        session.error = token.error; // Propagate the error state
    }
    return session;
},
```

#### Client-Side UX Strategy on Error

Client-side resilience requires monitoring the session error state. If a permanent token failure (e.g., failed RTT due to token revocation) occurs, the client must initiate re-authentication to ensure data security.

```typescript
// app/components/AuthWrapper.tsx
'use client';

import { useSession, signIn } from 'next-auth/react';
import { useEffect } from 'react';

export function AuthWrapper({ children }: { children: React.ReactNode }) {
    const { data: session } = useSession();

    useEffect(() => {
        // Monitor for the propagated error state [11]
        if (session?.error === "RefreshAccessTokenError") {
            console.error("Session error detected, forcing sign-in.");
            signIn(); // Redirect user to the login page
        }
    }, [session]);

    return <>{children}</>;
}
```

## 4\. Zero-Knowledge Authorization Strategy and Frontend Implementation

A core mandate of this architecture is adhering to a **Zero-Knowledge Authorization model**, where granular user permissions are never exposed to the client, thereby reducing the attack surface.

### 4.1. Authorization Model Rationale: Security by Minimal Disclosure

Authorization must be handled exclusively by the server as a **Policy Enforcement Point (PEP)**. Exposing the full list of roles or permissions, even in a cryptographically secured manner, creates significant risks:

  * **Information Enumeration:** Attackers gain visibility into internal system policy structures.
  * **Broken Access Control Mitigation:** Flaws in authorization logic are a leading web security vulnerability. By keeping the authority server-side, developers prevent unauthorized client-side tampering with role definitions.

In the Zero-Knowledge approach, the client only receives minimal identification claims (User ID, maybe a general role identifier like `role: "user"`) in the access token payload. Specific permissions required for UI gating (e.g., "Can I see the delete button?") are delivered as **context-derived booleans** alongside the requested application data, retrieved only from the authorized backend API.

The decision to avoid embedding granular permissions in the PASETO access token necessitates that the Go API performs a policy lookup (e.g., database read or cache check) on every protected request. This results in a minimal, justifiable latency trade-off in favor of **maximum security** (Zero-Knowledge).

| Feature | Pattern A: Token-Embedded Permissions (Standard) | Pattern B: Zero-Knowledge Authorization (Recommended) |
| :--- | :--- | :--- |
| **Permission Exposure** | High (Permissions list is visible in the client/network inspection). | **None** (Client only sees User ID/minimal claims). |
| **Authorization Enforcement Point** | Frontend (UI Gating) and Backend (API Check). | **Strictly Backend** (API Check, Policy Engine). |
| **Security Risk** | Higher risk of Information Leakage and Enumeration Attacks. | **Lowest** risk of client-side access control bypass/leakage. |

### 4.2. Secure Server-Side Rendering (SSR) Data Fetching

For high-performance initial page loads, Next.js **Server Components** handle authorized data fetching. This process leverages the `getServerSession` utility (or a helper function derived from it) to securely retrieve the necessary PASETO Access Token on the server.

```typescript
// app/dashboard/page.tsx (Server Component)
import { auth } from '@/lib/auth'; // Custom auth helper wrapping getServerSession
import { fetchProtectedData } from '@/lib/api'; 

async function ProtectedDashboard() {
    // Retrieve session context on the server
    const session = await auth(); 
    
    if (!session || !session.accessToken) {
        // Handle unauthenticated user flow (e.g., redirect to login)
        return <div>Access Denied</div>;
    }

    // Pass the PASETO Access Token for server-to-server API call
    const data = await fetchProtectedData(session.accessToken); 

    // Server-side data fetch function injects:
    // headers: { Authorization: `Bearer ${token}` }
    
    // Data Structure Returned by Go Backend:
    // { 
    //   "profileData": { /*... sensitive user data */ }, 
    //   "uiCapabilities": {
    //     "canEditProfile": true, 
    //     "canViewReports": false 
    //   } 
    // }
    
    return (
        <ClientComponent data={data}>
            {/* UI gating based on pre-fetched booleans */}
            {data.uiCapabilities.canEditProfile && <EditButton />} 
        </ClientComponent>
    );
}
```

### 4.3. Client-Side Authorization Checks (UI Gating)

The minimal boolean flags embedded in the fetched data payload (e.g., `canEditProfile`) are used by Client Components purely for **UX purposes**. This UI gating is **not security enforcement**. The Golang authorization middleware (Section 2.4) remains the mandatory, non-bypassable enforcement point for the actual API execution.

## 5\. Frontend Resilience and Performance with Tanstack Query

**Tanstack Query** is integrated to manage client-side asynchronous state, ensuring caching, request deduplication, and retry logic, thereby improving performance and system resilience.

### 5.1. Creating a Robust API Client with Token Interception

Client-side rendering (CSR) requests need to access the current PASETO Access Token for every API call. Since the token lives inside the Next-Auth session, an **Axios or Fetch interceptor** is used to dynamically inject the token into the headers before each request.

```typescript
// lib/apiClient.ts (Axios Interceptor Implementation)
import axios from 'axios';
import { getSession } from 'next-auth/react'; // For CSR context [23]

const api = axios.create({
    baseURL: process.env.NEXT_PUBLIC_BACKEND_API_URL,
});

api.interceptors.request.use(async (config) => {
    // Retrieve the latest session information
    const session = await getSession(); 

    // Inject the current PASETO Access Token [23]
    if (session && session.accessToken) {
        config.headers.Authorization = `Bearer ${session.accessToken}`;
    }
    return config;
}, (error) => {
    return Promise.reject(error);
});
export default api;
```

### 5.2. Interceptor Strategy for 401/Token Expiration Handling

The interceptor’s role regarding token refresh is simplified by relying on Next-Auth to handle the silent refresh internally via the `jwt` callback. The interceptor must focus on distinguishing between a temporary **401** (where Next-Auth is already refreshing the token) and a permanent **401** (where RTT has failed).

```typescript
// lib/apiClient.ts (Response Interceptor Implementation)

api.interceptors.response.use(
    (response) => response,
    async (error) => {
        const originalRequest = error.config;
        const session = await getSession();

        // 1. Check for 401 unauthorized status
        if (error.response.status === 401) {
            
            // 2. Check if the session indicates a permanent RTT failure
            if (session?.error === "RefreshAccessTokenError") {
                // Next-Auth confirmed the refresh token is revoked/expired [11]
                console.error("Permanent authentication error. Redirecting to sign-in.");
                await signIn(); // Force sign-in to resolve error
                return Promise.reject(error);
            }
            
            // 3. Temporary 401: Assume Next-Auth is handling the silent refresh.
            // Tanstack Query should simply retry the query. 
        }
        
        return Promise.reject(error);
    }
);
```

## 6\. Security Deep Dive and Risk Mitigation

### 6.1. Comprehensive Token Usage Summary

| Token | Type/Format | Storage Location | Read/Used By | Expiration | Primary Security Function |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **PASETO Access Token** | PASETO V2.Local (Encrypted) | Encrypted Next-Auth Cookie (Server/Client Context) | Next.js Server Components, Client API Interceptors, Go Backend Auth Middleware. | **Short** (e.g., 5-15 mins). | **Authorization**, Opaque proof of identity. |
| **Refresh Token** | PASETO/Opaque ID (Go defined) | **HttpOnly, Secure Cookie** (Set by Go Backend) | Next-Auth Server-Side `jwt` callback (indirectly via HTTP request to Go). | **Long** (e.g., 7-30 days), **Rotated on Use**. | Renewing the Access Token securely, **session integrity**. |
| **Next-Auth Session Token** | JWT (Encrypted) | HttpOnly, Secure Cookie (Next-Auth managed) | Next-Auth internal logic (`getSession`, `useSession`). | Matches Access Token expiry, extended on refresh. | Maintains user session state and token payload across requests. |

```
